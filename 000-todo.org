* TODO Analyze how alibfyaml interacts with libfyaml's zero-copy string handling
  libfyaml avoids copying strings wherever the decoded value coincides
  with the source bytes:

  - Parsed input: the source buffer isn't copied into a fresh buffer.
    For fy_document_build_from_string, the document keeps pointers
    directly into the caller-supplied string, which must outlive the
    document (confirmed the hard way: freeing it early produced
    garbage scalar values -- this is exactly the bug fixed in
    Libfyaml.Documents.Parse_String via the new Owned_Buffer field).
    For file input, the FYPCF_DISABLE_MMAP_OPT flag implies the
    default path mmaps the file rather than reading it into an owned
    buffer.
  - Scalars are pointer+length spans into that buffer, not allocated
    strings: fy_node_get_scalar returns a `const char *` plus an
    explicit length, not a null-terminated copy. A plain unquoted
    scalar's decoded value equals its source bytes, so it can just be
    a span into the original memory.
  - Copying only happens where required: quoted scalars with escapes,
    and folded/literal block scalars, can't be represented as a plain
    source span, so those do allocate/copy. This shows up directly in
    the API as paired functions like fy_node_create_scalar (no copy,
    caller's memory must stay valid for the document's lifetime) vs.
    fy_node_create_scalar_copy (copies, safe to free the source right
    away) -- alibfyaml currently only binds the _copy variant in
    Libfyaml.Documents.Create_Scalar.

  Need to analyze what this means for alibfyaml more broadly, beyond
  the one bug already fixed:
  - Are there other spots besides Parse_String where a buffer/string
    passed across the Ada/C boundary needs to outlive something it
    currently doesn't (Insert_At paths, mapping keys via
    fy_node_mapping_lookup_value_by_string, etc.)?
  - Should alibfyaml expose the non-copying fy_node_create_scalar
    (zero-copy construction) as an option alongside Create_Scalar,
    with clear Ada-side ownership/lifetime documentation, for callers
    who want to avoid the copy?
  - Document the general rule for binding consumers: which Node-
    returning accessors hand back data whose lifetime is tied to the
    Document's input buffer vs. document-owned storage.

* CANCELLED Resolve YAML 1.1 language-independent types: timestamp, binary, merge, omap, pairs, set
  The typed-scalar accessors in Libfyaml.Nodes (Is_Integer/Is_Float/
  Is_Boolean/Integer_Value/etc.) only resolve the YAML 1.2 core schema
  (null, bool, int, float) -- see the doc comment above them. They
  don't touch the YAML 1.1-era "language-independent types" tag
  repository: !!timestamp, !!binary, !!merge (<<), !!omap, !!pairs,
  !!set. Those were dropped from YAML 1.2's core schema and libfyaml's
  core layer doesn't resolve them either, so this would be new
  Ada-side resolution logic, following the same pattern as the
  existing typed accessors (Is_X predicate + X_Value raising
  Libfyaml.Data_Error on mismatch).

  Decided not to pursue any of the six:

  - !!merge, !!omap, !!pairs, !!set -- not interested; not useful
    enough for this binding to justify the work.

  - !!binary -- would decode base64 scalar text to raw bytes. Skipped
    because it needs two new pieces of infrastructure this project
    doesn't have yet rather than just a grammar check: a base64
    decoder (nothing in the codebase decodes base64 today) and a
    decision on what Ada type to hand the decoded bytes back as (no
    existing "byte string" convention here -- candidates are
    Ada.Streams.Stream_Element_Array, System.Storage_Elements.Storage_Array,
    or a String used as a raw byte buffer). Not just another *_Value
    function like Integer_Value/Float_Value.

  - !!timestamp -- would parse the YAML 1.1 timestamp grammar (full
    ISO 8601 forms, a space in place of T, a bare Z or +-hh[:mm]
    offset, a date-only form). Skipped because the natural return
    type, Ada.Calendar.Time, can't round-trip what the scalar actually
    says: Ada.Calendar.Time is a UTC instant, so it silently discards
    the source UTC offset (e.g. the "-05:00" in
    "2001-12-14t21:59:43.10-05:00" is lost once folded to UTC) and its
    sub-second precision is implementation-defined. Preserving the
    as-written value faithfully would mean returning a custom record
    (year/month/day/hour/minute/second/sub-second/UTC-offset) instead
    of a single builtin Ada type -- again more design work than a
    plain *_Value accessor.
