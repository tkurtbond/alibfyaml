* DONE Analyze how alibfyaml interacts with libfyaml's zero-copy string handling
  libfyaml avoids copying strings wherever the decoded value coincides
  with the source bytes:

  - Parsed input: the source buffer isn't copied into a fresh buffer.
    For fy_document_build_from_string, the document keeps pointers
    directly into the caller-supplied string, which must outlive the
    document (confirmed the hard way: freeing it early produced
    garbage scalar values -- this is exactly the bug fixed in
    Libfyaml.Documents.Parse_String via the new Owned_Buffer field).
    For file input, the FYPCF_DISABLE_MMAP_OPT flag implies the
    default path mmaps the file rather than reading it into an owned
    buffer.
  - Scalars are pointer+length spans into that buffer, not allocated
    strings: fy_node_get_scalar returns a `const char *` plus an
    explicit length, not a null-terminated copy. A plain unquoted
    scalar's decoded value equals its source bytes, so it can just be
    a span into the original memory.
  - Copying only happens where required: quoted scalars with escapes,
    and folded/literal block scalars, can't be represented as a plain
    source span, so those do allocate/copy. This shows up directly in
    the API as paired functions like fy_node_create_scalar (no copy,
    caller's memory must stay valid for the document's lifetime) vs.
    fy_node_create_scalar_copy (copies, safe to free the source right
    away) -- alibfyaml currently only binds the _copy variant in
    Libfyaml.Documents.Create_Scalar.

  Need to analyze what this means for alibfyaml more broadly, beyond
  the one bug already fixed:
  - Are there other spots besides Parse_String where a buffer/string
    passed across the Ada/C boundary needs to outlive something it
    currently doesn't (Insert_At paths, mapping keys via
    fy_node_mapping_lookup_value_by_string, etc.)?
    RESOLVED for both:
    - mapping keys (fy_node_mapping_lookup_value_by_string): safe as
      written. libfyaml's own header says the key argument is "the
      YAML source to use as key" and the lookup works "from the YAML
      node created from the @key argument" -- the key text is parsed
      into a transient node for comparison during the call itself, not
      retained afterward, so Libfyaml.Nodes.Value/Has_Key/Required's
      immediate CS.Free (C_Key) right after the call is correct.
    - Insert_At's path string: same reasoning, also safe to free
      immediately (libfyaml copies/parses the path before use, per the
      same pattern as the key case above). Insert_At turned out to
      have a real, different lifetime hazard instead -- not about the
      path string, but about the *target node* argument: libfyaml
      unconditionally unrefs it, and frees it outright if the
      operation fails. Fixed: Insert_At's N parameter is now "in out"
      and is nulled out on failure. See its doc comment in
      src/libfyaml-documents.ads.
  - Should alibfyaml expose the non-copying fy_node_create_scalar
    (zero-copy construction) as an option alongside Create_Scalar,
    with clear Ada-side ownership/lifetime documentation, for callers
    who want to avoid the copy?

    DECIDED: no. Create_Scalar already has to copy the caller's Ada
    String into a heap C buffer first (Ada strings aren't
    null-terminated, and are often stack-allocated) -- a no-copy
    fy_node_create_scalar would only save libfyaml's *second*,
    internal copy. Every existing call site builds a handful of
    scalars per document as one-off tree edits, not in a hot loop, so
    that saving has no concrete workload behind it. Making it safe
    would need new infrastructure Document doesn't have: a growable
    collection of Buffer_Refs (one per zero-copy scalar, kept alive
    for the whole document's life, since libfyaml gives no callback
    for "this node was removed, its buffer can be freed"). Not worth
    that complexity with no real need driving it -- see PLAN.md's
    "Zero-copy Create_Scalar" section. Create_Scalar stays copy-only.
  - RESOLVED: Document the general rule for binding consumers: which
    Node-returning accessors hand back data whose lifetime is tied to
    the Document's input buffer vs. document-owned storage.

    The answer, once actually investigated rather than just written
    up from what seemed true: there isn't a per-accessor rule a
    caller needs to track. Every Node is valid for exactly as long as
    its Document is, full stop, regardless of which of Parse_String/
    Parse_File/Document_Stream.Open_String/Open_File produced it --
    see the extended header comment in src/libfyaml-nodes.ads.

    Investigating this specific claim (not by inspection -- by
    actually checking the one case it implied and nothing tested)
    found it was FALSE for one case: a Document drawn from
    Document_Stream.Next, from a stream opened via Open_String,
    shared its buffer with the *stream* rather than owning a
    reference itself -- destroying the stream while such a Document
    was still alive was a genuine, silent use-after-free (confirmed
    live with valgrind). Fixed with a small reference-counted buffer
    handle (Buffer_Ref) shared between the stream and every Document
    drawn from it -- see PLAN.md's "Document_Stream buffer lifetime"
    section for the full writeup and src/libfyaml-documents.ads for
    Buffer_Ref itself. The rule as now documented is true because
    this fix makes it true, not because it always was.
* DONE Can alibfyaml be extended to read from existing Ada File_Type variables, like Current_Input and Standard_Input?
  Yes. New child package Libfyaml.Documents.Text_IO provides Parse
  (File : Ada.Text_IO.File_Type; Resolve_Anchors : Boolean := True)
  return Document, wired to libfyaml's fy_document_build_from_fp via
  the underlying C FILE* (Ada.Text_IO.C_Streams.C_Stream (File), a
  GNAT-specific bridge -- this is the one GNAT-only package in
  alibfyaml as a result, called out in its own header comment). Works
  for Current_Input and Standard_Input exactly the same as any other
  File_Type, since both are just File_Type values (confirmed live,
  including with a genuinely piped stdin under valgrind, not just the
  Set_Input-onto-a-real-file trick kept in test/test_text_io.adb).

  How it works with libfyaml's zero copy (confirmed against libfyaml's
  own source, fy-input.c, not assumed from its header comments): a
  FILE*-backed input is read lazily via fread() into a buffer libfyaml
  allocates and owns itself -- neither Parse_File's mmap of the whole
  file nor Parse_String's zero-copy span into the caller's own buffer.
  The returned Document therefore holds no reference into anything
  Ada-owned, and File need not outlive it. libfyaml does not close
  File's underlying stream either (confirmed: it only frees its own
  read buffer for this input kind) -- ownership stays with the caller.

  One real caveat found live while testing this, documented in
  Text_IO's own doc comment and not glossed over: libfyaml's fread()
  reads in whole internal chunks, not "exactly one document's worth"
  -- for most real files (anything smaller than one chunk) a single
  Parse call silently consumes the *entire remaining file*, not just
  the first document, leaving File at end-of-file. Calling Parse a
  second time on the same File to get a second document therefore
  does NOT work (confirmed live) -- it silently sees no more bytes,
  not an error. Correctly streaming multiple documents out of one
  FILE* would need libfyaml's other, persistent-parser API
  (fy_parser_set_input_fp + repeated fy_parse_load_document on one
  parser, the same shape Libfyaml.Documents.Streams.Open_File already
  uses for paths) -- not implemented, since the question that prompted
  this item was about reading a File_Type at all, not streaming
  multiple documents from one; cheap to add the same way if a real
  need for it shows up.

  Also found and fixed, unrelated to Text_IO itself: sharing
  Parse_Common between Parse_String/Parse_File and Text_IO.Parse
  needed Parse_Common to stop returning Document (a tagged type --
  RM 3.9.3(10) forbids a new private-part primitive of one's own
  package's tagged type) and return the raw Thin.Fy_Document handle
  instead, wrapped into a Document by each caller. That refactor
  introduced a real, if narrow, regression along the way -- see
  PLAN.md's "Parse_Common shared with Text_IO.Parse" section for the
  full writeup of a genuinely easy-to-miss Ada gotcha it exposed
  (a subprogram's own exception handler doesn't cover its own
  declarative part), confirmed live with valgrind and fixed before
  this item was considered done.

* CANCELLED Resolve YAML 1.1 language-independent types: timestamp, binary, merge, omap, pairs, set
  The typed-scalar accessors in Libfyaml.Nodes (Is_Integer/Is_Float/
  Is_Boolean/Integer_Value/etc.) only resolve the YAML 1.2 core schema
  (null, bool, int, float) -- see the doc comment above them. They
  don't touch the YAML 1.1-era "language-independent types" tag
  repository: !!timestamp, !!binary, !!merge (<<), !!omap, !!pairs,
  !!set. Those were dropped from YAML 1.2's core schema and libfyaml's
  core layer doesn't resolve them either, so this would be new
  Ada-side resolution logic, following the same pattern as the
  existing typed accessors (Is_X predicate + X_Value raising
  Libfyaml.Data_Error on mismatch).

  Decided not to pursue any of the six:

  - !!merge, !!omap, !!pairs, !!set -- not interested; not useful
    enough for this binding to justify the work.

  - !!binary -- would decode base64 scalar text to raw bytes. Skipped
    because it needs two new pieces of infrastructure this project
    doesn't have yet rather than just a grammar check: a base64
    decoder (nothing in the codebase decodes base64 today) and a
    decision on what Ada type to hand the decoded bytes back as (no
    existing "byte string" convention here -- candidates are
    Ada.Streams.Stream_Element_Array, System.Storage_Elements.Storage_Array,
    or a String used as a raw byte buffer). Not just another *_Value
    function like Integer_Value/Float_Value.

  - !!timestamp -- would parse the YAML 1.1 timestamp grammar (full
    ISO 8601 forms, a space in place of T, a bare Z or +-hh[:mm]
    offset, a date-only form). Skipped because the natural return
    type, Ada.Calendar.Time, can't round-trip what the scalar actually
    says: Ada.Calendar.Time is a UTC instant, so it silently discards
    the source UTC offset (e.g. the "-05:00" in
    "2001-12-14t21:59:43.10-05:00" is lost once folded to UTC) and its
    sub-second precision is implementation-defined. Preserving the
    as-written value faithfully would mean returning a custom record
    (year/month/day/hour/minute/second/sub-second/UTC-offset) instead
    of a single builtin Ada type -- again more design work than a
    plain *_Value accessor.
